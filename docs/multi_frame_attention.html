Multi-frame cross-attention — how to integrate N frames

This note lays out the core problem in the PoC design. When the cross-attention that worked on the Pair (2-frame) setting is extended to 3 or more frames, where does it tend to fail, and how does the literature address it?

Note on framing. Read the literature under the assumption that "the problem they are solving" and "the problem we are solving" do not match. Even under the same banner of calibration, the sensor size, output format, supervision signal, and scale are all different. Problems should be solved deductively from the problem itself; the methods in papers are not to be used verbatim but to be treated as raw material. This document is written not in the order of "the paper does X, so we imitate X" but rather "what does our problem need → given that need, what examples does the literature offer?".

1. Problem setting

Our task is pose-conditional residual prediction:

  • Input: query frame $A$ (image + LiDAR points) and target frame $B$ (image + LiDAR points), and a noisy relative pose hypothesis $\hat T_{AB}$
  • Output: for each point in $A$, a correction $\Delta uv$ to its projected position in the $B$ image + a covariance $\Sigma$
  • The pose is an input condition (not an output)

The design that works in the 2-frame case:

q = pt_A + PoseEmb(T_AB)              # pose-shift Q
KV = pt_B (+ img_B as deformable)
scores = Q @ K^T / √d + b_AB           # b_AB is a scalar bias
out = softmax(scores) @ V

When extending to 3 or more frames ($A, M, B$), the query is still $A$, but the KV now contains both $M$ and $B$. At this point:

  • Where and how the pose information is injected has a large effect on performance.
  • If we naively set KV = concat(pt_M, pt_B) and put a single softmax over it, the sub-pair $(A, M)$ attention ends up with a different Q, KV configuration than when it was trained as the 2-frame $(A, M)$ case, so the learned knowledge cannot be reused.

2. Naive extension that fails (current PoC)

q     = pt_A + PoseEmb(T_AB)         # ← the same Q regardless of which KV-frame we look at
KV    = concat(pt_M, pt_B)
ref   = [uv_M_hat_of_A, uv_B_hat_of_A]
bias  = [b_AM, b_AB]  (per-frame, added only to the KV side)
scores = Q @ K^T + bias_per_frame
softmax over [M ∪ B]

Problems: - Q only knows the $A→B$ pose. When it looks at $M$ it still uses the Q shifted by the $A→B$ pose → the $A↔M$ sub-attention becomes a different thing from the 2-frame $(A, M)$ case. - pose_bias can only add a scalar offset. It has no influence on the direction of Q (where to look). - The sampling MLP of deformable attention also learns the offset from Q alone. If Q only knows "I want to look at $B$", then the supervision on where to sample in the $M$ image becomes an incorrect signal.

Empirical: v55 (M=GT, loss only on A↔B) gives a +0.5px improvement. v64 (M perturbed, all 6 directions supervised) instead degrades (val_err worsens by ~3x). Keeping M as an "extra" auxiliary KV works, but integrating it properly breaks.

3. The correct approach (per-KV-frame Q)

for each KV frame k ∈ {M, B}:
    Q_k = pt_A + PoseEmb(T_{A→k})       # ← a different Q per KV-frame
    K_k = pt_k
    scores[..., k] = Q_k @ K_k^T / √d
attn = softmax(concat scores over k)
out  = attn @ V

With this: - The Q, KV of the $(A, M)$ sub-pair now match the 2-frame $(A, M)$ case exactly ← knowledge can be reused - Same for $(A, B)$ - Since a single softmax mixes them, the importance of each frame is set by the magnitude of scores (= the learned "which one to trust") automatically - pose_bias can remain as an auxiliary scalar

The same logic applies to deformable attention on the img side: the sampling is learned from the combination of the reference uv of each KV-frame and the (frame-conditional) Q.

(a) DUSt3R / MASt3R (Wang et al., CVPR 2024 / ECCV 2024)

Pair-only siamese decoder. The Q of view 1 only attends to the KV of view 2. Multi-view (>2) is handled by stitching pairwise outputs together. This is a strategy of avoiding "single Q, multi-KV" — equivalent to realizing our (b) via "separate forwards".

(b) MVS Transformers (MVSFormer, MVSTER, TransMVSNet)

The source view features are warped into the frustum of the ref view via plane-sweep / epipolar warping before attention. A source-specific warped feature volume is built for each (ref, src_k) pair → this is functionally equivalent to (b), in the sense that Q (or KV) is pose-baked per source view.

(c) GTA — Geometric Transform Attention (Miyato et al., ICLR 2024)

A design that conditions Q multiplicatively by a per-KV pose rotation. Equation (3) in the paper: $$\text{Attn}(Q, K, V) = \text{softmax}(Q P_q^k K^T / \sqrt d) V$$ Here $P_q^k$ is a pose transform that differs for each (query, key) pair. As shown in the figure, Q and K each carry a coordinate frame attached to the token itself (their respective camera frames), and the relative transform is applied before the dot-product. This is the clearest implementation of "Q's bias depends on KV".

Framing differences with our problem: - GTA assumes NeRF-like view synthesis (i.e., generating the pixel that corresponds to a given viewing pose). Q is "the pose of the pixel we want to output next", KV is the image features at known poses. The output is pixel value. - We do camera-LiDAR residual prediction. Q is the points of the anchor frame; KV is image+pt features of another view. The output is per-point Δuv + Σ. - The role of the pose input is "input condition (us)" vs. "rendering target (GTA)". The purposes differ, but the question of how to build pose-conditional attention is the same.

For that reason, GTA is not a method to borrow as-is — the multiplicative Q/K rotation form is less natural in our framework than an additive pose embedding form (our PointMLP / image features are learned representations, so applying SE(3) rotation directly to them has little meaning). However, the principle of "insert a pose transform per Q-K pair" can be carried over. Concretely, our (b) — building pt + PoseEmb(T_{A→k}) per KV-frame_k — corresponds to the additive version of GTA.

(d) Fast3R (Yang et al., CVPR 2025), VGGT (Wang et al., CVPR 2025)

They add a frame-id learnable embedding and concatenate all view tokens into a single sequence. Q is shared but a frame-id is added as a per-token bias (option c). Notable: pose is an output of the model, not an input condition. The premise differs from our use case, so it cannot be reused as-is.

(e) Pose-conditional baseline (Swin RPE, T5-style)

Scalar bias of relative position. Same kind as our current pose_bias. It is effective for small discrete offsets, but insufficient for continuous SE(3) pose — in particular, when rotation induces a depth-dependent pixel shift, a single scalar bias cannot correct for it.

5. Conclusion / Recommendation

Reasoning back deductively from the problem:

  1. Our task is already proven to work in the 2-frame case (v55=2.28). At this point the per-token attention path is established (Q=pt+pose_emb, KV=other frame, residual prediction head for Δuv+Σ).
  2. When extending to 3 frames, the sub-problems (A↔M), (A↔B) must each be the same problem as the 2-frame case. Otherwise the knowledge learned in the 2-frame case cannot be reused, and simultaneous optimization of the 6 directions has to be learned from scratch (= the reason v64 failed).
  3. "Keeping the sub-problem identical to the 2-frame case" means that the Q, K, V of the (A, M) sub-attention are bit-identical to those of the 2-frame (A, M) case. If Q holds only one pose, then when looking at M it still attends with the Q-shift meant for B → it becomes a different problem.

The form our problem demands: per-KV-frame Q (option b). This is functionally equivalent to the principle of GTA, but implemented as the additive pose-embedding version (rather than rotation multiplicative, since our token representations are outputs of learned MLPs, so additive is more natural).

Reasons for rejecting the other options: - (a) Shared Q + scalar bias breaks sub-problem identity and thus is not viable (it may happen to work for small poses, but breaks down at large angles / long baselines). - (c) Frame-id embedding is specialized to models that output pose (Fast3R/VGGT); for problems like ours that take pose as an input condition, it lacks information content.

Concrete rewrite:

# inside cross_blocks:
scores_blocks = []
for k, (frame_pt, pose_to_k) in enumerate(zip(pt_kv_list, poses_to_each_frame)):
    pose_emb_k = pose_mlp(pose_to_k).unsqueeze(1)
    q_k        = pt_query + pose_emb_k        # frame-conditional Q
    Q_k        = q_proj(norm_q(q_k))
    K_k        = k_proj(norm_kv(frame_pt))
    scores_blocks.append((Q_k @ K_k.transpose(-1,-2)) / sqrt(d))
scores = torch.cat(scores_blocks, dim=-1)     # softmax across all KV
attn   = softmax(scores) @ concat_V

With this, the attention flowing into the $(A, M)$ sub-pair uses exactly the same combination of Q, K as in the 2-frame case → the pre-train knowledge that lives in the pair model (v55 = 2.28) can be losslessly transferred to the multi-frame setting.
