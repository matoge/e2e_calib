1 model, N problems — positional query + multi-modal frame_token

TL;DR — By restricting the Query to embeddings derived purely from (uv, depth) and making the KV a modality-agnostic frame_token grid, cross-frame pose residual, camera-LiDAR extrinsic calibration, camera-Radar, and multi-camera calibration can all be solved with the same model definition (same code, same weight format). Verified on both calib and cross-frame on PandaSet 103 scenes.

1. What exactly is "the same"

The network being trained is a single CalibNetUnifiedFrame in models/cross_frame_unified.py. Across all problems below we use:

  • the same class CalibNetUnifiedFrame(...) instance
  • the same layer structure (frame encoder + N × deformable cross-attn + intra-frame self-attn)
  • the same output head (per-point (Δu, Δv, log σu, log σv, ρ))

Only two things change per problem: the way the dataset is constructed, and the modality flag passed to the encoder.

Problem Input frame_A Input frame_B Perturbation Output Verification
Cross-frame pose residual image + LiDAR (frame t1) image + LiDAR (frame t2) relative pose noise per-point Δuv (t1→t2) v304 (PandaSet 103)
Cam-LiDAR extrinsic calib image (frame t) LiDAR scatter (frame t, projected with perturbed extrinsic) extrinsic noise per-point Δuv v303 (PandaSet 103)
Cam-Radar extrinsic calib image (frame t) Radar scatter (frame t, projected with perturbed extrinsic) extrinsic noise per-point Δuv v305 (nuScenes 150, ARS 408 ×5)
Multi-camera calib ★ camera_A image camera_B image relative extrinsic noise per-point Δuv not yet verified (implementation patch is trivial by design)

★ = not yet verified. The implementation should work simply by setting the modality flag to 'cam'/'cam'.

2. Design core — separate Query and KV

2.1 Query is position-only (modality independent)

In the older model (cross_frame v100 series) the Query was constructed as:

Q[i] = bilinear_sample(frame_token_anchor, uv_i)  # ← local feature from anchor frame
     + PointMLP(uv_i, depth_i)                    # ← 3D positional info
     + pose_emb(target)                           # ← pose hint to target frame

Being a sum of these three, the bilinear_sample term implicitly assumes the anchor frame has multi-modal features (image + LiDAR fused). When the anchor is camera-only or LiDAR-only (as in calib settings), the feature bias distorts the query.

The new version (uv_only_query=True):

Q[i] = PointMLP(uv_i, depth_i) + pose_emb(target)

uses purely positional information. The query side has no knowledge of what modality is inside, so whether frame_A is image-only or LiDAR-only, the query is constructed identically.

2.2 KV is a fixed-shape frame_token grid

Each frame is collapsed into a single tensor of shape (B, D, 16, 16). Its content is:

frame_token[c, h, w] = fuse(image_feat[c,h,w],
                             lidar_scatter[c,h,w],
                             has_lidar_mask[h,w])

This fuse is a 1×1 Conv, with the image side initialized as identity at zero and the LiDAR side initialized to zero. A modality flag switches encoder behaviour:

  • 'mm': use both as usual
  • 'cam': forces lidar_scatter / mask to zero → image only
  • 'lidar': forces image_feat to zero → LiDAR only

(cross_frame_unified.py:96-129). The output shape is always (B, D, 16, 16) regardless of modality. The cross-attention side only ever sees this "same shape", so it operates independently of the upstream problem definition.

3. Empirical verification — same model works across 3 modalities / 2 datasets

With the identical model setting (CalibNetUnifiedFrame, uv_only_query=True, n_cross_layers=4, 1.65M params) we trained three variants in parallel:

  • cam-LiDAR calib (PandaSet 103)
  • cross-frame pose residual (PandaSet 103)
  • cam-Radar calib (nuScenes 150)

All use the same code, same model definition, same recipe.

Highlights:

  • Across all 6 combinations of 3 modalities (LiDAR / Radar / multimodal) × 3 datasets (PandaSet / nuScenes / combined) × single-cam ↔ all-cam (6/4/5 cameras), the same model definition and same recipe work.
  • Even for cam-Radar (nuScenes ARS 408 ×5, ~50-200 points/frame sparsity, 2.5D with zero elevation), we reach the same calib accuracy class as cam-LiDAR (0.61-0.71 px val_err). We simply scatter on a plane — zero cost for modality extension (as the §4.1 symmetry argument predicts).
  • Even for all-cam (PandaSet 6, DDAD 4, Waymo 5, nuScenes 6), we can jointly train on thousands of (scene, cam) pairs in a single model. With cameras='all', LiDAR / Radar / image from all cameras collapse into the same frame_token (front/rear/left/right symmetry is learned by the model itself).
  • Almost every run has val_NLL ≤ 1 (uncertainty σ is not overshooting) → the per-point Σ is calibrated, and downstream Σ-weighted PnP / BA works as-is.

Key points:

  • The same CalibNetUnifiedFrame(uv_only_query=True, n_cross_layers=4) achieves meaningful error reduction on both problems.
  • The weights are trained separately (head sharing not yet attempted) — even so, this refutes the inductive prior that "a different problem needs a different model".
  • v303's base 8.05 px → 0.68 px corresponds to cm-class calibration accuracy (img_size=64 patch, CROP=128-256 px, within 0.3° in typical focal-length terms).

4. Why it works

4.1 The "image vs LiDAR" symmetry

If we view camera-LiDAR calibration as the problem of "projecting LiDAR onto one image with two different extrinsics and predicting the difference", it becomes exactly equivalent to the cross-frame problem of "projecting one world point through two relative poses and predicting the difference". Written as equations:

Cross-frame:
   uv_B_GT  = π(K_B,  T_BW · X_world)
   uv_B_HAT = π(K_B,  T_BW · ΔT_pose · T_WA · X_cam_A)
   target   = uv_B_GT - uv_B_HAT

Cam-LiDAR calib:
   uv_GT  = π(K_cam,  T_cam_lidar_GT  · X_lidar)
   uv_HAT = π(K_cam,  T_cam_lidar_HAT · X_lidar)   = π(K_cam, T_cam_lidar_GT · ΔT_extr · X_lidar)
   target = uv_GT - uv_HAT

In both cases, target = π(GT) − π(HAT) = "pixel difference between the correct external transform and a perturbed external transform". As long as the target has this same form, the network only needs to learn a single residual primitive.

4.2 The frame_token design collapses "modality" to a single name

The upper half of the network (cross-attn onward) only sees frame_token. The output shape of frame_token is fixed at (D, 16, 16), and whether its content is image, LiDAR, or a mixture, the upper half treats it uniformly as "local features on a 16×16 cell grid". Differences arising from modality switching are absorbed inside the encoder; the upper half never notices.

This is exactly the same abstraction as ViT treating image patches as "uniformly arranged tokens" — whether the content is image, text (LiT), or audio (Whisper), the upstream transformer structure does not change.

4.3 Extension is just "adding a modality to the encoder"

To handle Radar, adding one Radar encoder branch (range-angle transform → grid scatter) is enough — the same model then handles cam-Radar calibration. For multi-camera calibration, the encoder simply takes two images (both with modality 'cam').

5. What changes — product-design impact

Old approach This design
Per-task specialized nets (CalibNet, MatchNet, PoseNet, ...) trained and operated separately A single residual-primitive net; only the problem definition changes upstream
Adding a new sensor (Radar / heterogeneous camera) requires redesigning a new net Just add a modality flag to the encoder. The upstream net is untouched.
Calibration / SLAM / mapping / loop-closure are separate systems in separate teams All can be solved with the same weights + different preprocessing

By folding "sensor / task symmetry" into the architecture, the spatial stack of robotics / autonomous driving becomes dramatically thinner.

5.5 Production recipe — pre-train (combined) → fine-tune (single dataset)

Combined-dataset training (v306 / v307b) is slightly worse than the per-dataset best (v303 / v304) (1.00 vs 0.67, 2.63 vs 2.54). The reason is that a single set of weights cannot fully absorb differences in the calib / sensor noise distribution across datasets.

We verified a production recipe to solve this:

  1. Large-scale pre-train: 30 epochs of M0 pair / M0 calib on a combined multi-dataset.
  2. Per-dataset fine-tune: fine-tune the weights on a single dataset at a low lr (5e-4) for 15 epochs.

Asymmetry of cross-modal transfer (v316 / v317):

direction val_err vs from-scratch vs same-modality fine-tune
LiDAR pre-train → Radar fine-tune (v316) 0.58 px better (v305 0.61) worse (v313 0.53)
Radar pre-train → LiDAR fine-tune (v317) 0.76 px worse (v303 0.67) worse (v311 0.60)

LiDAR → Radar is transferable because "a subset of an encoder that learned dense geometry is being used". Radar → LiDAR is information-poor because "an encoder that only saw sparse / planar data is being applied to dense / 3D". When doing cross-modal transfer without going through the same modality, place the higher-capacity representation side in pre-training.

Pre-train + fine-tune beats standalone training (winning in 3/3 compared cases):

  • v306's general-purpose geometry / appearance representation, learned across 1100 scenes × 3 dataset families × all-cam, sits inside the encoder.
  • Per-dataset fine-tune only slightly adapts to cam-specific noise / focal-length range → completed in a few epochs (a few minutes).
  • Practical for deployment in both memory footprint and training cost.

Deployment perspective:

  • Keep a single "base" weight on an in-house server.
  • Deploy to each dataset / each in-vehicle SoC via a few tens of minutes of fine-tuning.
  • New sensors / new regions can be added with the same recipe.

6. The map-based case — building frame_token "from the map"

So far we have discussed cross-attn between multiple observation frames. Replacing this with "frame_token coming from the map vs frame_token from the current observation" directly gives us a primitive for localization / loop closure / map update.

6.1 Map representation

What we accumulate over time can be any of:

  • A cloud of Gaussian Splats (μ_3D, Σ_3D, color or feature vector) — dense, high quality
  • Or point cloud + per-point features (color / descriptor)
  • Or a surfel mesh

Any of these will do. What matters is that it can be "collapsed into a frame_token given the current pose hypothesis".

6.2 Render at hypothesis pose → frame_token

T_world_to_cam_HAT (current pose hypothesis)  +  map (e.g. GS cloud)
   ↓
   Transform each splat / point into camera frame with T_HAT + project
   ↓
   Accumulate features on image plane (α-blend or scatter)
   ↓
   frame_token_map  (B, D, 16, 16)   ← same shape as existing encoder output

We place frame_token_map alongside the current frame's observed frame_token (conventional encoder over image + current-frame LiDAR) as the KV. Q is still position-only.

6.3 What comes out

Use case What to do
localization Render the map from the hypothesis pose → frame_token_map. Cross-attn with the observed ft → per-point Δuv → update pose with Σ-weighted PnP. Iterate.
loop closure verification Render the map at a candidate pose from place-recognition. If the inlier σ ratio exceeds the threshold, accept the loop. σ naturally becomes the rejection metric.
map update / change detection A patch with large residual between observation and map (large Δuv / small σ) means "different from the map" = dynamic change or missing mapping. Usable to decide whether to ingest a new observation or reject a dynamic object.
multi-session merge Maps built in different sessions can be aligned via observations in a shared area. Just feed session B observations into session A's map.

6.4 Comparison to LIVO / FAST-LIVO family — map optimization is the decisive difference

State-of-the-art LIDAR-Inertial-Visual Odometry like FAST-LIVO2 is purely geometric (ICP + photometric error + EKF / factor graph), using no network at all. More importantly:

LIVO systems "do not optimize the map"

System Map representation Map optimization
FAST-LIO2 ikd-tree point cloud No — accumulation only
FAST-LIVO2 LiDAR ikd-tree + visual patches LiDAR none / patches minimally
LIO-SAM point cloud No — only pose graph is optimized
R3LIVE++ point cloud + color No — IESKF accumulation
3DGS / Photo-SLAM Gaussian Rendering-loss gradient (bakes dynamic objects)
This design (proposed) GS or point cloud + features Σ-weighted residual gives gradients to pose / point position / point σ all together

What LIVO systems actually move:

  • ICP — assumes a static scene. Breaks with dynamic objects (heuristics required to remove them)
  • photometric — breaks under darkness / motion blur / reflection
  • IMU — connects to the map only through drift integration
  • Even when loop closure exists, it only shifts the pose trajectory; past map-point errors remain fixed

Advantages of this design:

  • σ separates dynamic objects / OOD by itself (no annotation needed, see §4.1) → dynamic objects are not baked into the map, and if baked they can be removed later because σ is large
  • Modality failure is absorbed by learning (dark camera → LiDAR-driven, rainy LiDAR → camera-driven)
  • Gradients flow into the map itself → drift does not become fixed in the map, and past map points can be corrected together via loop closure
  • Since the map side can be collapsed into a frame_token, no system redesign is needed when new sensors are added

In other words: a design for a network-augmented full SLAM (localization + map optimization + loop closure + sensor calib + dynamic object removal, all handled by one primitive) with a footprint as light as LIVO.

6.5 Edge deployment

CalibNetUnifiedFrame(d=128, n_cross_layers=4) = 1.65M params.

  • fp16: 3.3 MB
  • int8 quantized: 1.7 MB
  • 30+ FPS is realistic on the Jetson Orin Nano (8W) class
  • Automotive in-vehicle SoCs (Renesas R-Car / NVIDIA DRIVE) can handle it comfortably

A configuration where "map-based SLAM runs continuously in a vehicle" is a realistic size.

7. Known limitations / next steps

  • Modality weight-sharing experiments: Right now the weights for v303 and v304 are separate. We want to fine-tune both from a single checkpoint and measure how much of the multi-task can be shared.
  • Cam-Radar PoC: Implement a Radar modality encoder on AV2 (Radar 7 sensor) or in-house data, and train calibration with the same recipe.
  • Multi-camera calib: Train front/rear inter-camera extrinsic estimation with the same model on PandaSet 6cam. The in-house surround-view rig would be the same.
  • Inference-time mode switching: Build a sentry network that can perform calib / cross-frame / radar inference all from a single weight, cutting the edge deployment memory footprint by a factor of N.
