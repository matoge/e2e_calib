Unified frame-token architecture — val_err 2.27 → 1.85 px, val_nll 2.27 → 1.59

On a cross-frame residual prediction sub-task (= correcting where LiDAR points project into the image between adjacent frames) using PandaSet 39-scene front_camera, we pushed the previous best inside the cross-frame line — val_err 2.27 px / val_nll 2.27 (v55, the legacy multi-frame model, an old architecture from right after the cross-frame effort started) — down to val_err 1.85 px / val_nll 1.59 via three stages: frame-token unification + cross-attn depth scaling + multi-frame KV expansion.

Timeline: - Repository initial commit: 2026-04-10 - Cross-frame task started: 2026-04-24 (Fri) — v55 and other legacy multi models - Rapid improvement to unified frame-token: 2026-04-25 (Sat) — early morning of 2026-04-27 (Mon)

Terminology (self-contained)

Abbreviations used on this page:

  • val_err (px) — mean per-point pixel error on the validation set, mean(|pred_uv − gt_uv|). Lower is better.
  • val_nll — mean Gaussian negative-log-likelihood 0.5 z² + log σ + ... on the same points. Measures not only the error but also the correctness of the predicted σ. Lower is better.
  • C (= n_cross_layers) — how many cross-attention blocks are stacked in a single forward. Each block is one unit of cross-attn → self-attn → FFN → residual output. C=2 means 2 stages, C=4 means 4 stages. Depth corresponds to "thinking capacity."
  • N (= 1 + n_KV_frames) — total number of frames the model sees.
  • N=2: pair (only anchor A and target B)
  • N=3: triplet (A, B + one intermediate frame M added as KV)
  • N=4: quad (A, B + two intermediate frames M1, M2 added)
  • multi-frame KV — a structure that feeds intermediate frames M as the Key/Value of attention, letting the Query (derived from A) freely sample from multiple frames and reason like "this point is also visible in M, so use that side."
  • frame token — a representation that fuses each frame's image and LiDAR points onto the same 8×8 grid as a single tensor (D, 8, 8). Grid cells with no observation get 0 + a mask channel.

Legacy architecture (v55, the legacy multi model)

  • Image and LiDAR processed on separate paths:
  • Image: (D, 8, 8) coarse feature grid + MSDeformAttn
  • LiDAR: sparse point-token list (~256 items) + plain attention
  • Inside a single cross-block, q/k/v/o projections have two separate paths: one for image, one for LiDAR.
  • Plateaued at val_err 2.27 px / val_nll 2.27 (the best right after the cross-frame task started on Fri 4/24).

New architecture (unified frame-token, v70 and later)

Scatter LiDAR points onto the same 8×8 grid as the image (= average per-point features into the corresponding grid cell). By allowing "no observation = 0 + has_pt mask," the image and LiDAR are collapsed into a single frame_token (D, 8, 8). As a result:

  • The distinction between image and LiDAR disappears, and a single MSDeformAttn is enough for cross-attention.
  • The per-point Q is built by bilinear-sampling the anchor frame's frame_token and running a PointMLP.
  • Multi-frame: broadcast an absolute pose embedding relative to the anchor onto each KV frame's grid → a single softmax inside MSDeformAttn simultaneously decides "from which frame and where to sample."

Details: models/cross_frame_unified.py. Design discussion: docs/multi_frame_attention.md

Interpreting "deeper C makes multi-frame work"

The least obvious discovery of this project: merely increasing the number of cross-attention blocks C barely moves val_err. Only when multi-frame KV is present does depth start to matter.

pair (N=2) multi (N=3) Delta
C=2 val_err 2.35 (v70) val_err 2.38 (v74) ±0
C=3 val_err 2.36 (v71) val_err 2.09 (v75) −0.27 px
C=4 val_err 2.29 (v84) val_err 1.93 (v92) −0.36 px

What is going on

  • In pair mode (N=2), there is only one KV frame, so the attribution candidates for each pixel are simple. C=2 already fully handles that simple information, and increasing depth does not change the ceiling.
  • In multi-frame (N=3 and beyond), the model must compare multiple hypotheses such as "this location in target B?" vs "this location in intermediate M?".
  • C=2: a single stage has to do both "which hypothesis to attend to" and "refinement" simultaneously, compromising both. As a result it cannot handle the extra multi-frame KV and ends up the same as pair.
  • C=3: division of labor becomes possible — stage 1 for "matching check against M," stage 2 for "refinement toward B" — so M's information can finally be exploited → −0.27 px.
  • C=4: division of labor becomes even finer; the model can refine while comparing the confidence of M and B → −0.36 px.

In other words, "C functions as thinking capacity for integrating multi-frame information." With only one KV, no capacity is needed; with more KVs, capacity is required — a clean division of labor.

Why NLL drops dramatically at N=4 (quad)

In val_err, v100 (N=4) is only −0.08 px ahead of v92 (N=3), but val_nll drops disproportionately by −0.34 (1.93 → 1.59). This means the σ-calibration became correct by an order of magnitude:

  • Having two independent observations from intermediate frames M1 and M2 lets the model distinguish, per point, between "observation is consistent across all 3 frames = static" and "the position differs across frames = dynamic or occlusion."
  • As a result, small σ is assigned to static points and large σ to dynamic / uncertain points, neatly split → NLL drops.

This property directly feeds into Σ-weighted bundle adjustment and clean point-cloud map generation with dynamic objects down-weighted. For direct observations of σ behavior, see docs/dynamic_object_sigma.md.

Things not yet tried

  1. Retrain with motion-warped GT (in progress) — for dynamic objects (points inside PandaSet cuboids labeled Moving), rewrite uv_gt via the box's rigid transform A→B before training. The current model "predicts assuming no motion"; retraining with warped GT could make it motion-aware.
  2. 6 cameras simultaneously — currently only front_camera. PandaSet has 6 cameras. Whether 6× data + view diversification suppresses overfitting.
  3. Ceiling search at C=5 and above — tried once, but NLL training broke (σ output pinned to the clamp upper bound). Stacking five zero-init proj heads apparently prevents the sum from being learned properly; needs redesign.
  4. Prototype Σ-weighted BA — real map generation using the existing v100 σ. Clean static map + visualization of separated dynamic objects.
  5. Migration to company data (VLS-128 LiDAR) — whether we can fine-tune on Zenseact Open Dataset (= the same VLS-128 sensor).
