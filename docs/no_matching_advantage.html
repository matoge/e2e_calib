Pose-conditioned residual net — the significance of a "no matching" design

TL;DR — The various spatial tasks in autonomous driving / robotics (recalibration, HD-map updates, SLAM, loop-closure verification, and so on) can all be rewritten in terms of a single primitive: "predict, with high confidence, where a given point corresponds in the camera image." This project trains that primitive directly as a per-point (Δuv, Σ) output network. Feature matching, RANSAC, shadow descriptors, and heavy SLAM solvers — none of them are needed anymore.

1. Output samples

Validation outputs from model v100 (multi c4 quad) trained on PandaSet 39-scene front_camera. Each sample shows a single A→B projection pair:

For each point:

  • × (gray) = projected position under the static-scene assumption with a noisy pose hypothesis (= input)
  • + (blue) = network output (× corrected by Δuv)
  • ○ (green/red) = true B position (GT). green = inside 2σ ellipse / red = outside
  • Ellipse = 1σ / 2σ uncertainty (drawn from Σ)
  • Title "2σ-cover=XX%" = fraction of points whose GT lies inside the 2σ ellipse (ideal ~95%)

At a glance:

  • Points on static scene such as road surface have small ellipses, with + and ○ nearly overlapping
  • Points on dynamic objects have inflated ellipses, absorbing the offset within 2σ
  • Within a single object, σ and Δuv are output with a consistent distribution

2. What is it useful for (applications)

Simply obtaining accurate answers to "where does the same point correspond, and with what confidence" is enough to build downstream systems for the spatial tasks that arise in real autonomous driving:

Use case What it does
Recalibration Factory-set K, T_extrinsic drift over time. Per-point (Δuv, Σ) → Σ-weighted least squares fixes it in seconds per patch
HD-map updates Align new driving data against an existing map. Run Σ-weighted BA only on patches with changes — cheap daily incremental updates
Visual / LiDAR odometry Plug in as a residual head against per-frame pose hypotheses. Can iterate inside a BA layer
SLAM loop-closure verification Look at all-point σ against a candidate pose — instantly judge whether it is a "correct loop"
Dynamic-object down-weighting σ inflation separates motion / OOD on its own (no labels required)

In other words, the same network becomes a primitive that supports calibration / mapping / SLAM / odometry horizontally. There is no need to build a heavy dedicated system per task.

3. How it differs from existing methods

There has been a flood of research over the past five years on making feature matching learnable / avoiding it:

Family Representative methods Output Pose handling
Learned matchers LightGlue, RoMa, DKM Correspondence pairs + confidence Output (RANSAC)
Detector-free matchers LoFTR, ASpanFormer dense correspondences Output
Differentiable SfM DROID-SLAM, ACE dense flow + dense BA Output
Pair → pointmap DUSt3R, MASt3R 3D point map Output
Multi-view → all VGGT, Fast3R, Spann3R poses + intrinsics + 3D Output
Learned PnP PixLoc, DSAC* Direct pose regression Output
This method (this) per-point (Δuv, Σ) Input (conditioning)

Axis by axis, what is different:

A. Pose is an input (conditioning), not an output

This axis needs to be laid out carefully:

  • DUSt3R / VGGT / Fast3R: do not take pose as input; they directly regress a pointmap or pose from a set of images. They cannot be used for the use case of "refining a noisy initial pose" (there is no input channel for it in the first place)
  • DROID-SLAM: an exception that conditions on an initial pose and iteratively refines it via dense flow + a BA layer. Design philosophy is close
  • Learned matchers (LightGlue / LoFTR): pose is neither input nor output; they only produce correspondences from an image pair
  • Learned PnP (PixLoc / DSAC*): direct regression from image → pose, not intended for refinement

In other words, "refinement with pose as input" is only structurally similar in the DROID family; the others cannot do it by construction.

The essential difference from DROID is design philosophy:

  • DROID is complete as an end-to-end SLAM system. A dense flow network + a dense BA solver are integrated into a single unit
  • This method only outputs the primitive. The downstream solver is a separate layer

The important point here is that in this method dense BA is not needed:

Once per-point (Δuv, Σ) is available, pose can be recovered by solving just a single sparse Σ-weighted least squares over a few hundred points. There is no need to iterate dense BA; this works as a closed-form one-shot analytic solution (Σ-weighted PnP / extrinsic estimation) for calibration or per-frame pose refinement. Dense BA is a heavy problem that seeks bundle consistency across the entire scene, and is out of scope for this proposal.

Laid out side by side:

DROID This method
Output per-pixel dense flow + scalar confidence per-point (Δuv, 2x2 Σ)
Solver dense BA layer built in Per-use-case — sparse one-shot, patch BA, etc.
Expressiveness Reduces to isotropic weighting Keeps anisotropic Σ
Coupling flow net + BA layer fused primitive alone; solver is external
Use case SLAM only Shared across calibration / map / SLAM / loop verify

It is a choice of "where to draw the module boundary". This proposal carves out the primitive into a single piece, then swaps solvers per task — a design that emphasises deployment economics. Maintaining a single primitive is cheaper to operate than building a dedicated SLAM system for each task.

Supplement: handling the temporal axis (GRU vs cross-attention)

DROID and this proposal can also be contrasted from an architectural point of view:

  • DROID stacks time recurrently with a GRU. It sequentially updates flow + pose at t = 0, 1, 2, ...
  • This proposal integrates multiple KV frames (M1, M2, ..., B) in parallel via transformer cross-attention. Time is put onto the KV axis of attention rather than being recurrent

Roughly speaking, one could think of it as "DROID's GRU replaced with a transformer and sparsified". Common ground: aggregating information over time to refine per-frame output.

Trade-offs:

  • transformer + parallel KV: parallelises well on GPU. N frames in a single forward pass
  • GRU recurrent: the time axis is (theoretically) extensible without bound. However, long sequences tend to vanish/explode, and parallelisation is hard
  • This proposal handles long time horizons via chain composition (sliding N=4 windows). Standard windowed-transformer pattern

B. The output is "residual + uncertainty", not "scene reconstruction"

DUSt3R outputs a 3D point cloud; VGGT outputs the entire scene. This method outputs only a local residual against a pose hypothesis. Reconstructing scene structure is handled as a separate task placed on top. In exchange, it functions as a lightweight layer that can rapidly evaluate "a different pose hypothesis for the same scene" or "the same point evaluated in a different frame".

C. It removes the matcher's premise of "visible in both"

By construction, matchers assume that "the same point is visible in both images" when establishing correspondence. Out-of-view motion, occlusion, and large viewpoint differences are all discarded as "no correspondence".

This method starts only from one-sided (A) query points and outputs the projected position + uncertainty under the pose hypothesis. For static scenes, uv can be computed from geometry even under occlusion (though image-side evidence is missing, so it is one-legged). Only for dynamic objects is the "static assumption fundamentally broken", so σ increases. This is not a hard inlier/outlier decision but rather expressed as a continuous σ value.

D. It does not learn invariance to viewpoint change

Descriptor-based systems internally learn the invariance that "the same 3D point produces similar descriptors even when the viewpoint changes". This tends to break at large angles. This method takes pose as input, so there is no need to solve "viewpoint changes" via invariance.

4. How it works

Inputs and outputs

Input:
  query frame A  (image + LiDAR)
  target frame B (image + LiDAR)
  relative pose hypothesis T_AB_hat  (noisy is OK)

Output:  for each query point
  Δuv  ∈ ℝ²    : correction to projected position in B image
  Σ    ∈ ℝ²ˣ²  : 2D covariance of correction (confidence)

(Δuv, Σ) is a natural parameterisation of a 2D Gaussian. It plugs directly into Σ-weighted least squares / Gauss-Newton / Levenberg-Marquardt optimisation tools. There is no need to interpose RANSAC or an inlier threshold.

Supplement: correspondence with 3D Gaussian Splatting (3DGS)

Gaussian Splatting is another representative example of the "represent the world with distributions rather than points" design: GS is on the scene side (Gaussians for 3D rendering); this method is on the matching side (Gaussians for 2D residuals). Their application domains differ, but they share the same design principles:

  • Holding each element as a distribution rather than a point explicitly carries local uncertainty
  • Analytically differentiable → connects directly to end-to-end training or downstream BA
  • Set operations (weighted averages, product, marginalisation) can be written using the closure of Gaussians

Both stand on the same intuition that "the world is better handled by promoting points to distributions".

Architecture — frame tokens + multi-frame deformable attn

Each frame is encoded as a frame_token in which image + LiDAR are unified on the same 8x8 grid. Empty cell = 0 + has-pt mask. Multiple KV frames are deformably sampled and integrated by cross-attention. Details: models/cross_frame_unified.py, docs/unified_progression.md, docs/multi_frame_attention.md.

Why a single network can solve it — the multi-layer structure of the Transformer

"Taking a pose hypothesis as input and producing per-point Δuv + σ in one shot" is a non-trivial task, and it is solved by the cross-attention structure of depth = thinking steps:

  • Step 1: what is around the position projected by the pose hypothesis? (candidate sampling)
  • Step 2: is it consistent with another frame M as well? (consistency check)
  • Step 3: where and by how much should the pose hypothesis be corrected? (residual refinement)
  • Step 4: output final σ as confidence (calibration)

This is the same structure as reasoning depth in LLMs. Tasks that are impossible in a single shot are solved by stepwise composition.

Experimental support (details: docs/unified_progression.md):

                pair (KV=B only)    multi (KV=M+B)
C=2  val_err :  2.35              2.38           <- same
C=3  val_err :  2.36              2.09           <- multi starts to help
C=4  val_err :  2.29              1.93           <- extends further
N=4 (M1+M2+B), C=4 :              1.85, val_nll 1.59 (all-time best)
  • In pair (single KV) depth is flat: each layer only sees the same evidence, so labour cannot be divided
  • In multi (KV=M+B) depth kicks in monotonically: division of labour into "consistency check" and "refinement" emerges per layer, and depth functions as thinking capacity
  • NLL jumps sharply at N=4 (2.0 → 1.6): the 3-frame consistency check cleanly allocates static / dynamic. Structurally impossible for matcher-based methods, which only produce pair-wise correspondences

5. Training data — scalable with public datasets alone

Supervised learning needs GT poses and GT uv for each point. These can be constructed without dedicated annotation:

Short-baseline GT is high accuracy

Consecutive frames (A, M1) (0.1-0.5 s, distance 1-5 m):

  • LiDAR point-cloud overlap 80%+ → GICP converges almost perfectly (mm-level error)
  • IMU drift is also <1 cm within 0.5 s
  • → the true value of T_{A→M1} has mm- to cm-level accuracy

Long-baseline GT is built by chain composition of short baselines

Chain A → M1 → M2 → ... → M_k → B:

T_{A→B} = T_{A→M1} ∘ T_{M1→M2} ∘ ... ∘ T_{Mk→B}

100 m baseline = 30 hops × 3 m → composition of 30 factors. Because GICP aligns the point clouds as anchors at each hop, drift does not accumulate systematically. In practice, after 30-hop composition the final error stays < 10 cm @ 100 m baseline (= angle 0.06°, pixel 1-2 px).

Residual GT noise vanishes by the law of large numbers

Composition error cannot be made exactly zero, but it is not serious for supervised learning:

  • The GT error e_i for each (A, B) sample is zero-mean (GICP is not biased)
  • With N independent samples in training → the mean error converges as O(1/√N)
  • With 1M samples × σ_GT ~ 1-2 px, the trained network can in principle reach 0.001-0.002 px accuracy

In other words, "GT noise disappears with data volume". Combining 5 public datasets (PandaSet, Waymo, nuScenes, AV2, DDAD) yields 1500+ scenes; adding ZOD grows it further. Natural data diversity (weather, geography, sensor specs) avoids the need for photometric augmentation or hard negative mining.

Dynamic objects are handled by box tracking

Public datasets come with 3D bounding-box annotation + uuid tracking. Points inside a box of a dynamic object (attributes.object_motion = Moving) can have their GT updated by warping with the rigid transform of the box (details: docs/dynamic_object_sigma.md). The "dynamic object → reject" step that matchers required is not needed.

6. Constraints

Wrong use case

  • Fully visual-only systems (no LiDAR / IMU / odometry): there is no means of producing an initial pose, so a visual matcher or photometric SLAM is required. This method sits in the downstream stage that "refines the side already holding a pose" — it is not a competitor, just a different use case

Engineering trade-off

  • Compute cost: matchers are cheap for obtaining correspondences per pair. This method requires a forward pass per pose hypothesis (heavy if called frequently inside a BA iteration). However, the unified architecture can be batched in parallel, and this is not a problem on modern GPUs
  • Out of training distribution: for sensor configurations or unusual environments (heavy rain, blizzards) not covered in training, σ may come out large. Retraining on the relevant data is required

PoC-setting caveat (interpretation of reported numbers)

  • The intermediate frame M's pose is passed as GT during training. The 1.85 px / 1.59 nll of v100 are values under the noise-free setting of M's pose hypothesis. In production, pose_AM would also be noisy (the A↔M baseline is short, so accuracy should be high, but not zero)
  • There is no supervision directed at M. Currently the loss is only bidirectional A↔B; M is provided only as KV. A design that supervises all 6 directions (including A↔M, B↔M, M↔A, M↔B) was tried separately, but with the stacked path the σ output became unstable, so we currently use the legacy triplet (M=KV-only)

These are not fundamental problems but engineering issues that can be fixed step by step:

  1. First train this method on short baseline A↔M (= already done in the v55 / v70 line, stable operation)
  2. Use those weights and incorporate M as "a second evidence source passed with noisy pose" into A↔B training (= curriculum learning)
  3. Finally extend the loss to the M↔A, M↔B directions as well

Running these in sequence brings both pose_AM noise handling and M-supervision online.

And the core claim of this article — "putting intermediate frames as KV causes a jump in accuracy from multi-frame information integration" — does not depend on this caveat. The phenomenon in which val_err, which plateaued in pair (no M), drops significantly in multi (with M) points in the same direction in both the M=GT-pose setting and the noisy-pose setting (= multi-view consistency leverages thinking depth). The PoC setting only affects the absolute numbers; the qualitative conclusion does not shift.

Rebuttal to the misunderstanding that "a matcher is needed"

It is often said that a matcher is needed at long baselines (>100 m + large angular differences), but:

  • This can be solved by extending the chain of intermediate frames. Adding 2 Ms in v100 improves val_err by 0.45 px, and N=5 improves it further. This suggests that arbitrary baselines can be handled by lengthening the chain
  • By lining up multiple Ms around a candidate loop pose, if all (Mi, Mi+1) residuals align with low σ, we can judge "correct loop"
  • A matcher is structurally unnecessary

7. Why has this not been published before?

To the best of my knowledge, there is no prior paper that directly does this combination (pose input + 2D Gaussian output + cross-modal supervised + chain composable). Guesses at the reasons:

  • The visual-only research community (mainly CVPR / ICCV) does not have LiDAR, so a cross-modal supervised setup cannot be assembled
  • LiDAR-heavy industry players (Waymo / Cruise / Aurora) may well have this kind of network internally, but it is not published
  • Public datasets in which "short-baseline GICP-refined pose + dynamic-object box tracking" are jointly available have only become usable relatively recently (Waymo v2, PandaSet, AV2, ZOD) — the timing at which the community would notice this combination

In other words, the novelty lies not in a theoretical breakthrough but in a specific combination of engineering choices tailored to the modern sensor stack + the state of public data.
