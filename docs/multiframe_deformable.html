Multi-frame Cross-Attention — Design Note

2026-04-25 revised edition — a design that extends pair-net to multiple frames with minimal changes. This note is the scaffolding for building a mapping pipeline that ships as a product as fast as possible. Not aimed at chasing paper novelty, but choosing a design that is lightweight / symmetric / interpretable.

1. Problem setting: pose estimation and productization of maps

Commercially, two layers of deliverables are required:

  • per-frame pose — real-time; once distilled it runs on CPU. A foundational capability that applies to autonomous driving / robotics / AR alike
  • persistent map — aggregated in the cloud offline; high-precision point cloud + color + semantic tags. The product itself (HD map, persistent anchors for robots)

The core of both deliverables is the (μ, Σ) correspondence coming out of pair-net. Pose can be solved immediately by an external BA; the map is built by accumulating (μ, Σ) in the world frame and then polishing. The model side plays the role of providing per-pair correspondence priors.

2. The current pair-net and its elegance

Each query is a LiDAR point P (known in 3D), projected into reference frame B via a hypothesized relative pose → cross-attention within a patch → outputs the residual (Δuv, Σ):

   query frame A                 reference frame B
   ┌─────────────┐                ┌─────────────┐
   │  patch_A    │                │  patch_B    │
   │  • • • • •  │ ── pair-net ─▶ │  ⊕  μ  Σ    │
   │   queries   │                │  ⊕   ⊕      │
   └─────────────┘                └─────────────┘
   perturbation on pose_AB_hat
Structural wins of pair-net:
  • matching skip — the query is a LiDAR point = a unique ID, so there is no need to search for "where is the same point on the other side." The classical SfM/SLAM's biggest difficulty is erased by construction
  • Project with the pose hypothesis → residual = observation. Correspondence emerges by definition, no search
  • The per-pair forward is distillable to CPU
  • (μ, Σ) can be passed directly to a classical BA; Σ-weighted GN works properly

3. Limits at long-baseline

When a pair (frame_A, frame_B) has an 80 m baseline (10 Hz × 80 frames class):

  • Parallax / occlusion cause patch appearance to differ significantly
  • With a narrow FoV, "half of the features visible in frame_A are out of frame in frame_B"
  • Large error in the hypothesized pose shifts the projection anchor
  • Correspondence is ambiguous for repetitive objects (poles / street lamps / guardrails)

A canonical hard case: the pole-tree scenario

Five identical poles, with a tree (identifiable) 5 m behind them:

  1. frame_t1: the second pole from the right is in front of the tree
  2. After 3 m of travel, frame_t2: the third pole from the right is in front of the tree
  3. The poles look identical; the only cue is their positional relation to the tree
Naive pair-only: given frame_A and frame_B alone, the "identical poles" cannot be distinguished. The model will confidently mis-match (small Σ, wrong μ) as "the same pole." BA trusts these confidently-wrong correspondences to estimate pose → drift grows. BA has no cognitive layer, so it cannot solve problems that the model has failed to disambiguate.

4. Four candidate solutions

OptionMechanismProsCons
(A) pair-only + short-baseline chain Many pair-net invocations over short links → estimate each pose → chain via BA Zero model change, high accuracy on short links Compute grows N×, requires dense FoV, correspondence errors cascade in ambiguous pole cases
(B) pair × N + fuse in BA Independent pair-net from one anchor to N refs → BA fuses all pair outputs Symmetry preserved, existing model reused Each pair does not see other frames → no cognitive layer, ambiguity remains
(C) multi-frame joint input + internal softmax fusion (this proposal) Concat KV of N frames into a single transformer, express inter-frame relative pose via RPE bias, fuse across all frames in one softmax Disambiguation inside the model, pole-tree case solvable KV volume × N, attention cost grows linearly
(D) DROID-SLAM family Recurrent dense flow + differentiable BA, trained through BA SOTA Heavy, real-time is tight, GRU-based interpretability is low

(A) is wasteful, (B) lacks a cognitive layer, (D) is too heavy. We adopt (C).

5. Chosen approach: multi-frame joint input + internal softmax fusion

5.1 Mechanism

                    fuse N frames in softmax
                    ┌──────────────────────┐
                    ▼                      │
   Q (anchor point P) ─────► attention ────┤  next layer (repeat)
                              ▲
                              │
   KV_all = concat(KV_B, KV_C, KV_D, ...)
        each KV token carries frame ID + 3D position info
        per-pair pose bias (RPE) on each (Q, K) pair

5.2 RPE (Relative Position Encoding) preserves symmetry

Add a per-(Q, K) bias to standard cross-attention:

# standard attention
scores = Q @ K.T / sqrt(d)              # (N_q, N_kv)
# multi-frame extension: pair pose bias
bias[q, k] = pose_mlp(pose_{frame(q) → frame(k)})    # scalar
scores += bias
attn = softmax(scores) @ V              # fuse all frames inside softmax

This is the same schema as Shaw+2018, T5 [Raffel+2020], and RoFormer-family RPE. No Q-shift needed, no KV-shift needed, and frame ID embedding is subsumed by the bias. The relative pose information of each (i, j) pair is injected dynamically during attention computation, and softmax completes the fusion.

5.3 Stacked layers for progressive disambiguation

   layer 1: sample all frames independently → softmax fuse → updated Q1
   layer 2: re-attend from Q1 → softmax fuse → updated Q2
   layer 3: ...

At each layer, Q evolves into "features that reflect the consensus across all frames." The pole-tree case is disambiguated across layers: layer 1 finds "the tree is a stable anchor," layer 2 finds "pole positions relative to the tree," layer 3 finds "different poles per frame" — resolution climbs step by step.

5.4 Efficient variant: level=frame deformable

For large N (5+), full attention blows up KV memory by N×. Using sample-based deformable [Zhu+2020], we sample only 4-8 offsets per (Q, frame_i):

  • Line up the (H, W) of N frames in spatial_shapes (= each frame becomes a level)
  • reference_uv_i = π(pose_A→i, P) as the per-frame anchor
  • Fuse via softmax over (frame × n_points) — functionally identical to full attn, but lightweight

Compute is O(N_q × N × n_points), linear in N, without the weight of concatenating KV. Unlike the temporal warping approach of PETR/PETRv2 [Liu+2022/2023], we keep each frame as an independent level and let attention build consensus — that is the key (PETRv2 collapses time via pose-warp).

6. How to inject position — relative info only

Absolute 3D coordinates must never be injected. If they are, the model learns scene-specific coordinates (Tokyo / SF / Osaka etc.) and cross-scene generalization breaks. The elegance of pair-net is that it works using relative pose alone. We preserve this principle in the multi-frame extension.

SidePosition infoAbsolute? Relative?Encoding
Q (point in frame_i) local uv in frame_i (or uvd normalized to [0,1]) frame-local (not absolute coordinates) PointMLP(uvd_in_local)
KV (token in frame_j) local uv in frame_j frame-local 2D PE on image feat
(Q, K) bias relative 6-DoF pose from frame_i → frame_j relative only pose_mlp(pose_{i→j}) → scalar bias

Each token declares "I am at frame-local uv X," and the bridge between frames is only the relative pose bias per (Q, K) pair. This is exactly the NLP RPE (Relative Position Encoding [Shaw+2018, T5 [Raffel+2020]]) extended to 3D pose. The absolute frame_id index does not appear in embeddings either; if needed, it can be implicitly distinguished by the magnitude / direction of the relative pose.

6.1 Contrast with the PETR family (absolute 3D)

The PETR / PETRv2 [Liu+2022/2023] family embraces the opposite philosophy:

  • Back-project each camera image pixel into an absolute 3D ray in the ego frame → add as position embedding to features
  • Multi-camera fusion is attention in the absolutized 3D space
  • Temporal fusion warps past features by ego motion to align to the current frame's absolute 3D

Because scene-specific (per-sample) absolute coordinates are recomputed every time, training is stable, but the design depends heavily on camera intrinsics calibration accuracy and is optimized for detection within a single scene. For mapping, where we need cross-scene generalization (one model for all roads in the world), this is unsuitable.

PETR family (absolute)This proposal (relative only)
Position embeddingAbsolute 3D ray in ego frameFrame-local uv only
Cross-frame fusionPose-warp + concat in absolute spaceInject relative pose bias into attention
Cross-scene generalizationDepends on scene-specific calibrationScene-invariant (relative only)
Primary use3D detection (per-scene)mapping / SLAM (cross-scene)

6.2 Unifying pair (N=1) and multi-frame (N≥2)

Current pair-net: q_A = pt_A_fused + pose_emb_AB ← this pre-shifts Q. This is the operation of "bringing Q into K's frame," and is mathematically equivalent to an attention bias:

# equivalent transformation
version A (current pair-net): score = (Q + pose_emb_AB) @ K.T
version B (RPE bias):         score = Q @ K.T + (pose_emb_AB @ K.T) — the K-independent portion is absorbed into the dot product
                              ≈ Q @ K.T + b(pose_AB)

In multi-frame, K spans multiple frames, so pose_emb differs per K → pre-shifting Q means duplicating Q as many times as there are Ks, which is inefficient. The RPE bias form (score += b(pose_{frame(q) → frame(k)})) works with a single Q, and extends naturally to N≥2. The pair (N=1) case is the special case of this bias form and is equivalent.

Conclusion: never inject absolute coordinates into tokens or attention computation; all inter-frame information flows only through the (i, j) relative pose bias. This lets us handle pair through multi-frame continuously within the same mechanism — scene-invariant, lightweight, and elegant.

7. Depth-optional mode (LiDAR / radar / stereo / mono / none)

In commercial deployments, the sensor configuration differs per vehicle. A single model must handle them all:

SensorDepth accuracy (σ_d)Primary customer segment
LiDAR (VLS-128 / Luminar)±2 cm denseAV OEMs, MMS
Radar (4D imaging)±10-30 cm sparse, robust in rainADAS, low-cost vehicles
Stereo±5 cm near-range, distance-dependentRobotics, mid-tier vehicles
Mono + learned depth±20-50 cm, scale ambiguityLow-cost, legacy footage
Camera only (no depth)—Legacy, AR

7.1 Unified representation

Each query point is passed as five values (uv, μ_d, σ_d, has_d). The sensor type is expressed via the value of σ_d:

σ_d = sensor_sigma(sensor_type, depth)
    LiDAR  : 0.02 m
    radar  : 0.20 m
    stereo : 0.05 m × (depth/30)²
    mono   : 0.30 × depth
    none   : ∞ (has_d = 0)

7.2 Modality dropout during training

Stochastically drop depth / vary σ_d per sample:

if rng.random() < p_drop_d:
    σ_d = INF; has_d = 0       # vision-only sample
else:
    σ_d = sensor_sigma(...);   has_d = 1

PointMLP takes 5-ch input (uv, μ_d, σ_d, has_d)

The FrustumLocalEncoder box filter ignores the depth axis when has_d=0, using only UV for neighborhood judgment. Where depth is missing, Σ_uv is naturally trained to spread wider.

7.3 Combined with multi-frame

When depth is entirely absent, reference_uv_i is not a single point but an epipolar line (the 1 DoF of depth is unresolved). Implementation idea: use a depth prior (e.g. 1-80 m) to lay 3-5 sample anchors along the line, and extend the deformable's n_levels to frame × depth_bin. depth_bin = 1 with LiDAR, 4-5 without.

Triangulation across multi-frame observations eliminates depth ambiguity → Σ_d shrinks = Bayesian update happens inside attention. This is essentially the same as the view consistency in GS-family methods, except there is no per-scene optimization; it is finished in one feed-forward.

8. Extension to dynamic objects

3D bbox tracks (from nuScenes/AV2/Waymo annotations) are expanded to per-LiDAR-point labels:

  • Attach is_dynamic, track_id, box_pose_t1, box_pose_t2 to each query point
  • For dynamic points, reference_uv_i is projected via the box pose, not the ego pose
  • Same model for static and dynamic points, with only different pose hints
  • On the BA side: dynamic points contribute per-object pose graph factors, static points contribute ego-pose factors → joint optimization

The model structure is unchanged. Only reference_uv computation and BA factor construction are extended. On the dataset side, a box-to-point label expansion helper is about 100 lines.

9. Role of BA — fusion, not cognition

The intent of not putting BA inside the model (= the DROID way) design:

  • Cognition (disambiguation) = inside the transformer — softmax fusion + multi-layer iteration build multi-frame consensus, with ambiguous correspondences reflected via large Σ
  • Fusion (6-DoF pose extraction) = 1-step BA — a Σ-weighted Gauss-Newton over already-disambiguated (μ, Σ), fusing all observations at cost O(N_q × N), lightweight

This separates responsibilities: the model is "the machine that emits good observations," BA is "the machine that pulls out the optimal estimate." Since BA never tries to solve complex correspondence problems, failure modes are few.

Why pair-only + iterative BA is insufficient: The approach of chaining many short-baseline pairs and stitching them via BA (option (A) above) works in theory, but (1) in urban environments with repetitive patterns each pair's correspondence is ambiguous and BA drifts, (2) heavy use of short links makes compute O(N²), (3) narrow FoV / occlusion breaks the chain — all making quality assurance difficult. A multi-frame transformer + 1-step BA absorbs all of these via internal softmax.

10. Implementation scope and PoC

Phase 0 — already complete (pair-net only)
  • v42 ckpt: PandaSet 109 scenes, stratified subsample + dense LiDAR frustum, best val_err 2.63 px
  • Effectiveness of frustum-full confirmed at commit 8e81d48
Phase 1 — multi-frame support (~150 LOC, 2-3 days)
  • models/cross_frame.py: add N reference frames to forward (extend current 1-ref to N)
  • RPE bias: pose_mlp outputs a scalar bias, added to attention scores
  • (efficient mode) extend deformable's spatial_shapes to N×L, reference_uv per-frame
  • datasets/pandaset_pair.py: add triplet/quadruplet sampling
  • Verify wide-baseline effect via baseline_sweep.py / chain_vs_direct.py
Phase 2 — dynamic objects + map polish (~300 LOC, 1 week)
  • 3D bbox annotation parser (nuScenes/AV2), per-point track labeling
  • 1-step BA solver (pure torch, reuse gn_pose_update from existing baseline_sweep.py)
  • Accumulated point cloud + rule-based polish (ground fit / floating-point cut / free-space carving)
  • Map quality evaluation (re-localization accuracy)
Phase 3 — polish for commercialization (~1-2 months)
  • Distilled CPU version (per-frame pose for edge GPU/CPU)
  • Cloud polish pipeline (GS-style colorization, shape fixed for light weight)
  • Customer-vehicle calibration support tool (our e2e_calib itself)
  • Map versioning / update mechanism

11.5 Risks

  • LiDAR required as a premise → mitigated by vision-only mode; initially only LiDAR-equipped vehicles
  • Depends on customer calibration quality → e2e_calib itself becomes the on-ramp tool, bundled with the product
  • Map versioning → update mechanism needs design
  • Weak IP defense → even if the mechanism is public, we differentiate through operational know-how, lock in with SaaS
